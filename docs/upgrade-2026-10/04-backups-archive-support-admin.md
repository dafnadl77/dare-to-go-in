### סיכונים (לפי חומרה)
1. **אין גיבוי אוטומטי של המסד והתמונות.** תקלה, מחיקה בטעות או השבתה = אובדן אפשרי של חלומות ותמונות של משתמשים אמיתיים. הפתרון בלי עלות: להריץ את הסקריפט שלי במחשב שלך אחת לשבוע.
2. **תמונות לא ב־Git ולא בגיבוי DB.** כל גיבוי שלא כולל Storage חלקי.
3. **פרויקט חינמי של Supabase עלול להיעצר (pause) אחרי תקופה ארוכה בלי פעילות** **[לאמת במסמכי Supabase העדכניים ובלוח]**. חוזרים ממנו ידנית, אבל בזמן העצירה האתר לא עובד.
4. **גיבוי ה־JSON שיצרתי מכיל hash של סיסמאות.** מאוחסן מחוץ לפרויקט בלבד. מומלץ להצפין את התיקייה (BitLocker/7-Zip עם סיסמה) או להעביר לכונן חיצוני.
5. 12 תמונות יתומות מבדיקות (ללא חלום מקושר) עדיין ב־Storage. חסרות סכנה, רק ניקיון.

### תוכנית גיבוי ללא עלות (לאישור)
- `scripts/backup-dare.mjs` כבר נכתב ונדחף (קומיט `336f444`): קורא בלבד, מייצא את הטבלאות, חשבונות Auth וכל התמונות עם מניפסט ו־sha256, ומסרב לכתוב בתוך תיקיית הפרויקט.
- הפעלה: ב־PowerShell, כשהמפתח רק בחלון ההוא:
  `$env:SUPABASE_SERVICE_ROLE_KEY = "…"` ואז `node --env-file=.env scripts/backup-dare.mjs "C:\Users\DAFNA\DARE-backups\2026-10-12"`
- אוטומציה: Windows Task Scheduler שבועי. המפתח **לא** נשמר בקובץ: הוא יבוקש בהפעלה (או שמור ב־Windows Credential Manager, החלטה שלך).
- שחזור: מסמך קצר יתווסף אחרי שתריצי ותאשרי שהגיבוי נראה לך תקין. **טרם נבדק שחזור מלא בפועל.**

## 3. שאילתות תמיכה (קריאה בלבד, להרצה ב־Supabase SQL Editor, בלי עלות)

```sql
-- 1) מצב חשבון לפי אימייל (בלי תוכן חלומות)
select u.id, u.email, u.email_confirmed_at is not null as verified, u.created_at, u.last_sign_in_at,
       c.balance
from auth.users u left join public.dream_credits c on c.owner_id = u.id
where lower(u.email) = lower('EMAIL_HERE');

-- 2) הזמנות ותשלומים של החשבון
select o.id, o.package_id, o.amount_ils, o.credits, o.status, o.provider_status, o.provider_tx,
       o.created_at, o.paid_at, o.granted_at, o.review_reason
from public.payment_orders o join auth.users u on u.id = o.owner_id
where lower(u.email) = lower('EMAIL_HERE') order by o.created_at desc;

-- 3) יומן קרדיטים של החשבון
select l.created_at, l.delta, l.reason, l.external_ref
from public.credit_ledger l join auth.users u on u.id = l.owner_id
where lower(u.email) = lower('EMAIL_HERE') order by l.created_at desc;

-- 4) הזמנות ששולמו אך לא נסגרו (דורשות בדיקה ידנית)
select id, owner_id, package_id, review_reason, review_tx, review_amount_ils, review_at
from public.payment_orders where review_reason is not null and status <> 'granted';
```

## 4. הצעה לממשק ניהול מאובטח (לא נבנה, לא שונו הרשאות)

עקרונות: קריאה בלבד, מבוסס על `app_owners` הקיים, ללא גישה לתוכן חלומות, כל פעולה נרשמת ב־`app_owner_audit` הקיים.

מסך אחד, ארבעה אזורים:
1. **חשבון:** אימייל, סטטוס אימות, תאריך הרשמה, כניסה אחרונה, האם זכתה בחלום החינמי.
2. **יתרות:** יתרה נוכחית, מספר חלומות שנוצרו (מספר בלבד, לא תוכן), יומן קרדיטים.
3. **רכישות:** הזמנות, סטטוס, `provider_tx`, `review_reason`.
4. **שגיאות:** ניסיונות ניתוח שנכשלו (מזהה ותאריך בלבד), הגבלות קצב שהופעלו.

מגבלה טכנית שמצאתי: **יש בדיוק 12 פונקציות ב־`api/` והמגבלה בתוכנית Vercel החינמית היא 12.** נקודת קצה חדשה לניהול מחייבת איחוד נתיבים קיימים (למשל נתיב אחד `/api/support` עם `action`) כדי לא לעבור את המגבלה ולא לשדרג תוכנית. אפשרות ללא קוד ובלי עלות עד שיש צורך: השאילתות שבסעיף 3.

מה לא יכלול: חיפוש בתוך חלומות, צפייה בתמונות או בטקסטים, שינוי יתרה ידני (אפשר להוסיף "תיקון קרדיט" בנפרד עם אישור כפול ורישום ביקורת).

### מה מחכה לאישור שלך
1. הרצת הגיבוי השבועי עם מפתח ה־service שלך (פעולה שלך: אני לא מחזיק את המפתח).
2. האם לבנות ממשק ניהול, ובאיזה היקף. עד אז: השאילתות.
3. נוסח מדיניות שמירה (גיבויים, רשומות תשלום).
4. האם לבדוק בלוח Supabase את תוכנית הגיבוי והעצירה, ולעדכן אותי (אין לי כלי שקורא את זה).
